# micro-harness 与其他 harness 的区别

> **一句话版本：** 我们不是最强的 harness。我们是那个你能一口气读完、并且能亲眼看着它长成平台、而可读的内核没有被丢掉的那一个。

这是一篇**设计对比**，不是跑分页。凡涉及别人的 harness，都引用其公开文档（见[资料来源](#资料来源)）；凡涉及我们自己的，都指向你现在就能打开的代码。

---

## 真正能区分 harness 的五个问题

罗列功能会让所有 harness 看起来一样。下面这五个问题才能把设计分开：

| # | 问题 | 它决定了什么 |
|---|---|---|
| 1 | **核心自己拥有能力吗？** | 如果连 agent 循环本身都可替换，你在做一个*运行时*；否则你在做一个*应用*。 |
| 2 | **扩展的单位是什么？什么时候加载？** | DI 容器、注册式 API、构造函数调用，是三种成本结构完全不同的产品。 |
| 3 | **事件是拿来干嘛的？** | 调试日志？可观测契约？还是**扩展面本身**？ |
| 4 | **历史怎么管理？** | 压缩、分支、回放——以及"模型真看到过的东西"是否被完整留档。 |
| 5 | **生成的代码怎么落地？** | 沙箱还是 worktree，以及**谁决定应用哪些**。 |

## 我们抄了什么，从谁那抄的

**从 dsh —— 事件管线。** dsh 把每个阶段都做成插件可观察的事件点。我们独立走到了同一个形状，而它现在是我们仓库里真正承重的想法：一条带标签的 `AgentEvent` 流，每个视图都只是它某个切片的纯函数。GUI 的回放拖动条和 agent 树不是外挂在循环上的功能，它们只是另外两个消费者。

**从 dsh —— 能力接缝。** 它的表述很精确，值得原样引用：*接缝 = 一种可替换的能力，含三个角色：声明接口的 Service Definition、实现它的 Service Provider、以及使用者 Consumer（通常是对模型可见的工具）*。我们把它原样用在了文件系统上：

```
FileSystem（接口）  →  localFs | worktree | 远端沙箱 | 内存测试替身
                              ↓
              read_file / write_file / list_dir   （模型看到的工具面）
```

收益是可测的：`packages/core/test/fs.test.ts` 让**真正的** `read_file`/`write_file`/`list_dir` 跑在一个纯内存文件系统上，完全不碰磁盘；而沙箱规则始终来自 provider 而不是工具。于是"worktree 子 agent"从工具里的特例，变成了**换一个 provider**。

**从 pi —— "adapt it, don't fork it"。** pi 的目标就是"不改它内部就能扩展"，而它的扩展面（工具、命令、事件处理器、UI、npm 包）本身就是产品。我们抄了这个目标，也抄了它诚实的约束版本：pi 用启动时加载的注册式 API 做到，我们用编译期接口做到。成本结构不同，承诺相同。

**从 pi —— 压缩是有损的，完整记录要留着。** `/compact` 做摘要，并且明确说"完整历史仍在 JSONL 里"。我们的 JSONL 同样是追加式，而且压缩**从不改写已经发给 provider 的内容**——这同时也是让 prompt cache 继续有效的原因。

**从 Codex —— worktree 隔离。** 每个 agent 一份工作副本，并行的 agent 因此不会互相覆盖。

## 我们刻意没抄的

### DI 容器 —— 我们做了一个，量了一下，删掉了

P1 是一个自研插件内核：**396 行代码 + 10 个测试**——`provide`/`get`/`inject`、生命周期（`waiting → active → failed`）、带 `fork()`/`isolate()` 的作用域、事件总线、config schema 校验。刻意做成 Cordis 的形状，为了保留迁移路径。

然后我们量了它到底承不承重：

| 测量 | 结果 |
|---|---|
| `@micro-harness/kernel` 被外部引用 | **1 次**，而且是 `import type` |
| 插件对象与注册表的运行时消费者 | **0**（各自只被自己的测试引用） |
| 仓库里的装配点 | **25** 个（`new Harness(` ×14、`new AgentRunner(` ×4、`createServer(` ×7） |
| 加一个新能力时这 25 处要改几处 | **0** —— 因为每个依赖都是"可选 + 有合理默认值" |

容器只买一样东西：**运行时组装**——能力在进程活着的时候来去，于是"加一个能力"从改代码变成改配置。它的**全部**其他好处都是这一条的衍生。而我们对"有人会在不重编译的前提下加能力吗"的诚实回答是：没有。

常见的反驳是 MCP。但 MCP 客户端就是*启动时读配置 → 连接 → 合并工具列表 → 退出时关闭*，构造函数十行就够。只有当 MCP server 必须**热插拔**、掉线还要从运行中的 agent 手里撤回工具时，容器才回本。那是个真实需求，而当时我们没有它。

所以我们留下了**接缝**、删掉了**容器**，并把触发条件写进了 ROADMAP，而不是留着投机代码：*如果将来能力必须在运行时来去，就从 `5df4ba9` 恢复内核，并**按那个真实需求**重写它，而不是按想象的需求。*

### 一个"什么都不拥有"的核心

dsh 的"没有需要打补丁的特权核心"对"必须承载任意模型、任意循环、任意 UI"的运行时是自洽的。而我们的循环是 268 行，它恰恰是别人来读的那个东西。把它变成插件，会藏起我们最想让人看见的那个文件。

## 属于我们的东西

1. **一份可读的种子，以及由它长出来、且可证明不是 fork 的平台。**
   `seed-v1` 是这个仓库上的一个 tag：17 个文件、零依赖、无构建步骤，`node src/cli.ts "…"` 直接能跑。`main` 是它的**直系后代**（种子的文件在 P0 被*搬进* `packages/core`，而且仍是同样的四个模块）。这份对比里没有第二个项目同时提供"一口气读完整套 harness"**和**"同一份代码是一个跑起来的平台的地板"。

2. **把"模型可见即被记录"做成能打开看的功能，而不是纸上的不变量。**
   dsh 写了这条规则；我们把它实现成一等事件。每次模型调用都发出 `model.request`，带精确载荷——system prompt、工具 schema、**裁剪之后**的消息数组、以及 harness 自己的 token 估算。它被刻意排除在检索索引之外，避免上下文转储污染 `/api/search`；GUI 的 **检视** 面板逐轮渲染它。它的孪生兄弟是回放：整个视图可以从事件流的任意切片重建。

3. **不会悄悄误应用的逐 hunk 审阅。** 隔离让每个 agent 有自己的 worktree，而**审阅这一步才是更有意思的那一半**。`packages/core/src/patch.ts` 把 unified diff 解析成全局编号的 hunk，并且只把**被接受的**那些回放到文件的**当前**内容上。old side 已经不匹配的 hunk 会以 `conflicted` 返回、原样不动——它**拒绝**而不是猜——结果再走和整体 promote 相同的 integrate 路径，于是备份和冲突报告都是白送的。已针对真实 `git diff` 输出验证过：新建文件、删除文件、多文件 diff、上下文漂移。

4. **接缝，而不是容器——而且附上凭证。** 那个被删掉的内核，连同数字和"什么时候把它请回来"的触发条件，都写在上文。多数项目会一直留着投机的抽象层、再也不过问；我们公开了这次测量和这次回退。

5. **把经济性当一等公民。** 三家厂商用三个不同的字段名上报 prompt cache 命中；这里统一归一化成 `usage.cacheRead`、按缓存价计价、并在界面上显示命中率。还有两个与之配套、真正让缓存命中生效的决定：工具结果在**写入时**就被截断（之后永不重写），压缩丢的是**中间**而不是前端，于是头部始终是稳定的前缀。本仓库真实运行实测：三次调用命中 **75% / 78% / 69%**，而按缓存计价的结果比它替换掉的"所有输入都是未命中"算法便宜约 **2 倍**。

## 我们不确定的地方

比起暗示自己没有疑问，我们更愿意把疑问写下来。

| 问题 | 什么能给出答案 |
|---|---|
| 编译期接缝，能满足一个真实的第三方"不改代码就想加能力"的需求吗？ | MCP 那一轮。如果"就是启动时读配置"成立，那对我们来说容器始终不必要；如果有人需要往**运行中**的进程里加能力，内核就回来。 |
| "确定性地丢中间"比"把旧轮次摘要化"更好吗？ | 评测集。我们的方案可测且对缓存友好；摘要化可能保留更多语义，代价是一次模型调用和非确定性的记录。没有测量就不该宣称谁赢。 |
| 随着平台变大，冻结的种子还能保值吗？ | 一个新人是否仍能一口气读完 `seed-v1`，**并且**在里面认出今天的平台？如果两者开始脱节，这个 tag 就只剩考古价值。 |
| 逐 hunk 审阅的面积，值不值得它占的地方（相比"直接用 git 看 diff"）？ | 使用情况。这是我们**最不确定值不值**的一个功能。 |
