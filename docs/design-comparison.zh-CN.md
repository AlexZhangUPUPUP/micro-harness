# 设计笔记：micro-harness 与其他 harness 的取舍

> 这是一篇**设计对比**，不是跑分。凡涉及其他工具的部分，均引自其公开文档或源码，并在文末列出出处；这些项目都在快速演进，本文是一次带日期的快照，如有出入欢迎指正。凡涉及我们自己的，都指向你现在就能打开的代码。

一句话：micro-harness 的目标不是"最强"，而是**把一个完整 harness 保持在可通读、可验证的规模**——内核不被平台替掉，每个设计决定都能在仓库里被复核。

---

## 区分 harness 的五个问题

罗列功能会让所有 harness 看起来一样。下面五个问题更能区分设计：

| # | 问题 | 它决定了什么 |
|---|---|---|
| 1 | 核心是否自己拥有 agent 循环？ | 循环可替换 → 你在做一个**运行时**；否则是一个**应用**。 |
| 2 | 扩展的单位是什么、什么时候加载？ | DI 容器、注册式 API、编译期接口，是三种成本结构完全不同的选择。 |
| 3 | 事件用来做什么？ | 调试日志、可观测契约，还是**扩展面本身**。 |
| 4 | 历史怎么管理？ | 压缩、分支、回放，以及"模型真正看到过的内容"是否留档。 |
| 5 | 产出的改动怎么落地？ | 沙箱还是 worktree，以及**谁决定应用哪些**。 |

## 我们从社区借鉴了什么

设计不是凭空来的。下面每一条都注明出处，以及我们把它用在哪。

**事件驱动的循环（源自 dsh）。** dsh 把流水线每个阶段都做成可观察的事件点。我们独立收敛到同一形状，并让它成为仓库里真正承重的结构：一条带标签的 `AgentEvent` 流，每个视图都只是它某个切片上的纯函数。GUI 的回放滑杆和 agent 树不是挂在循环上的功能，而是另外两个消费者。

**能力接缝的三段式（源自 dsh）。** 其文档对"接缝"的定义很精确：一个可替换能力由 Service Definition、Service Provider、以及 Consumer 三个角色组成。我们把它落到了文件系统上：

```
FileSystem（接口） →  localFs | worktree | 远端沙箱 | 内存测试替身
                            ↓
            read_file / write_file / list_dir（模型看到的工具面）
```

收益可测：`packages/core/test/fs.test.ts` 让**真正的** `read_file`/`write_file`/`list_dir` 跑在纯内存文件系统上，沙箱规则来自 provider 而非工具本身。"worktree 子 agent"因此从工具里的特例变成**换一个 provider**。

**"适配而非 fork"（源自 pi）。** pi 的扩展面（工具、命令、事件处理器、UI、npm 包）本身就是产品。我们采纳了这个目标，并接受其诚实的约束版本：pi 用启动时注册的 API 实现，我们用编译期接口实现——成本结构不同，承诺相同。

**压缩有损，完整记录要留（源自 pi）。** `/compact` 做摘要，并明确说明"完整历史仍在 JSONL 里"。我们的 JSONL 同样是追加式，且压缩**从不改写已经发给 provider 的内容**——这也是 prompt cache 能持续命中的原因。

**worktree 隔离（源自 Codex 等）。** 每个 agent 一份工作副本，并行时互不覆盖。

## 有意的取舍

### 上过 DI 容器，量完之后删掉了

P1 是一个自研插件内核：396 行代码 + 10 个测试，包含 `provide`/`get`/`inject`、生命周期、作用域、事件总线与配置校验，刻意做成 Cordis 的形状以保留迁移路径。随后我们量了它是否承重：

| 测量 | 结果 |
|---|---|
| `@micro-harness/kernel` 被外部引用 | 1 次，且是 `import type` |
| 插件对象与注册表的运行时消费者 | 0（各自只被自己的测试引用） |
| 仓库里的装配点 | 25 个 |
| 新增一个能力需要改上述几处 | 0——依赖都是"可选 + 有默认值" |

容器只买一件事：**运行时组装**。其余好处都是它的衍生。而"会不会有人在不重编译的前提下加能力"这个问题的诚实答案是：在我们的场景里，不会。

常见反驳是 MCP。但 MCP 客户端本质是"启动时读配置 → 连接 → 合并工具 → 退出时关闭"，构造函数十行即可。只有当 MCP server 需要**热插拔**、掉线还要从运行中的 agent 手里撤回工具时，容器才回本。

所以我们保留了**接缝**、删掉了**容器**，并把恢复条件写进 ROADMAP，而不是留下投机代码。

### 我们选择让核心持有循环

"没有特权核心"对"要承载任意模型、任意循环、任意 UI"的运行时是自洽的。但我们的循环只有 344 行，它正是希望被人读到的那部分；把它改成插件会让这个文件更难被看见。这是一个明确的偏好，而非对错。

## 我们认为自己不同的地方

1. **一个可通读的种子，以及可证明是从它长出来的平台。** `seed-v1` 是本仓库的一个 tag：17 个文件、零依赖、无构建步骤，`node src/cli.ts "…"` 即可运行；`main` 是它的直系后代（种子的文件在 P0 迁入 `packages/core`，仍是同样的六个源码文件）。

2. **把"模型可见即被记录"做成可查看的功能，而不是文档里的一句话。** 每次模型调用都发出 `model.request`，携带精确载荷——system prompt、工具 schema、裁剪后的消息数组、以及 harness 自己的 token 估算。它被刻意排除在检索索引之外，以免上下文转储污染 `/api/search`；GUI 的**检视**面板逐轮渲染它。与之配套的是回放：整个视图可以从事件流的任意切片重建。

3. **不会悄悄误应用的逐 hunk 审阅。** 隔离让每个 agent 拥有自己的 worktree，而**审阅是更有意思的一半**。`packages/core/src/patch.ts` 把 unified diff 解析成全局编号的 hunk，只把**被接受的**回放到文件**当前**内容上；old side 已不匹配的 hunk 会以 `conflicted` 原样返回——它拒绝而不是猜。已针对真实 `git diff` 验证：新建/删除文件、多文件、上下文漂移。

4. **把经济性当作一等公民。** 三家厂商用三个字段名上报 prompt cache 命中，这里归一化成 `usage.cacheRead`、按缓存价计价并在界面显示命中率。配套的两个决定让缓存真正生效：工具结果在**写入时**截断（之后不重写），压缩丢**中间**而非前端。本仓库真实运行三次命中 75% / 78% / 69%。

## 尚不确定的地方

| 问题 | 什么能给出答案 |
|---|---|
| 编译期接缝能否满足真实的"不改代码加能力"需求？ | 已有初步答案：就当前场景而言可以。MCP 即"启动时读配置"，`main.ts` 一句 `connectMcpServers()`，循环、工具注册表、事件契约与 GUI 零改动；已对官方参考 server 验证（13 个工具，模型调用 `everything__get-sum` 得到 `42`）。若将来需要热插拔，恢复条件见 ROADMAP。 |
| 确定性"丢中间"是否优于把旧轮次摘要化？ | 已带消融实测：两者都能在长会话里保住埋在前面的约束，而不保留开头会丢失它。`summarize` 成本相近但上下文峰值更高；我们仍以确定性的 `drop-middle` 为默认，需要保语义的任务可用 `--compact=summarize`。 |
| 种子会随平台变大而失效吗？ | 一个新人是否仍能一口气读完 `seed-v1`，并在其中认出今天的平台。若两者脱节，这个 tag 只剩考古价值。 |
| 逐 hunk 审阅是否值得它的面积（相比直接用 `git diff`）？ | 使用情况。这是我们最不确定的一个功能。 |
